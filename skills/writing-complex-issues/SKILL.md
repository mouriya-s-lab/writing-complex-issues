# 编写复杂 issue

## 标准

**issue 必须无状态：headless 环境、零额外指令、只看 issue thread（body + 全部 comment）不偏离。**「不偏离」指偏离目标，不是偏离某个预钉的实现——issue 是任务目标，不是预知未来。

issue 必须同时给出三层：**业务**（为什么值得做、做成后谁观察到什么）、**架构**（这是系统的哪个部件、在哪条边界上、防什么漂移）、**代码锚点**（已知事实钉在哪）。细节可以迭代时定，业务和架构不可以。

**本方法用失败模式与代价引导，不用禁令围栏。**每条默认值都带理由；偏离默认值是允许的——条件是说得出例外的理由并记录在 thread 里。格式告诉你必须回答什么问题，不规定答案长什么样。

## 硬基线

与模型强弱无关的卫生底线，每条附失败模式：

- **一个 issue 一个问题。** 拼盘的症状：多段互不相关的动机各自论证不同的 fix、标题用「和 / + / 、」拼话题、会有多个 PR 因完全独立的原因来关它。判断法：能否写出一段连贯的「背景 / 为什么」论证整个 body？Why 自然裂成「第一个问题、第二个问题」就拆——原子 children + 一个 umbrella 说明它们为什么属于一起。
- **引用原文，否则不声称。** 每句动机话可追溯到真实来源（issue/PR body 的某行、commit、log 抓取），格式 `> "..." — repo#N` / `repo@sha`。转述允许，伪造引用与跨源拼接句子不行——headless 读者拿引用核实事实，假引用让范围建立在虚构上。两条引用矛盾时在 body 里点出矛盾，不糊过去。
- **parent 必须是 issue，且单 parent。** sub-issue API 拒绝 PR 当 child、拒绝第二个 parent；PR 经 body 的 closing keyword（`Closes #N`）挂 issue，一个 PR 关一个 issue。树画出「PR 有 children」即重画。
- **标题与 body 不放内部脚手架。** 草稿 id、agent ID、源树临时路径——操作员在 GitHub 直接读 body，脚手架是过不了 review 的噪声；引用 sibling 用标题或真实 issue 号。
- **高风险假设先 spike。** 依赖未文档化第三方行为、跨环境连通性、或「should work / presumably」式推测语言时，spike child 先行并 Blocks 实现（形态见 references/child-body.md）。
- **正文中文，固定 token 英文**（代码标识符、路径、命令、`repo#N`、`Depends on` / `Blocks`、`RFC:` 前缀、维度名）。语气 terse imperative：已落地用过去时，计划工作用祈使句，无营销腔、无未来承诺式表述。

## 内容三分类（写每句话前先归类）

| 类 | 定义 | 默认处置 |
|---|---|---|
| a：已知事实与约束 | 动机、架构不变量、代码锚点、已裁决的目标级决策 | 写，且自包含（契约逐字快照，指针的代价是每跳一次引用就多一个偏离点） |
| b：本质自由的实现细节 | key 命名、命令拼写、内部结构 | 默认不写——写了就成虚假约束，封死更优实现；想写先用判据升格为 a |
| c：不实验不知道的 | 第三方行为、跨组件可行性、性能 | 标记未知 + 实验路径 + 结果分支——伪装成已知的洞要执行到才炸 |

a/b 判据：**这个分叉的不同选择会不会改变操作员观察到的结果**。详细流程（可判定性测试、全局求解）见 references/decision-closure.md。

## 路由

下层文档**不是可选参考**：命中情形即必读——区块定义只存在于对应文档里，跳读等于凭印象写区块，缺口会漏到 headless 执行时才暴露。唯一的可选性来自「情形本身不发生」，每行写明何时可不读、为什么那时安全：

| 情形 | 必读 | 何时可不读（及为什么安全） |
|---|---|---|
| 开树：写 umbrella/RFC body | references/umbrella-body.md | 仅当树已有 umbrella 且本次不动它——区块由既有 body 承载，无需重写 |
| 写或改任何 child | references/child-body.md | 仅当本次不产出 child——没有要写的 body 就没有要遵守的区块 |
| 补齐/修订 thread（决策、架构切片、log 义务、设计修正） | references/comment-layers.md | 仅当本次只产 body 草稿且补齐显式留给后续会话——但完整 thread 是交付标准，后续会话必须回来读 |
| 收口「归 PR 定 / 待定 / 再说」类留白 | references/decision-closure.md | 仅当全文扫描后确认零留白——扫描本身不可省（自检清单含这条），SKILL.md 的三分类速查只够写作归类，不够做收口 |
| 写完后的对抗审查 | references/adversarial-review.md | 不可省——新树未过审查不算完成（思维方式第 4 条）；仅操作员显式说只要草稿时可延后 |
| 落地 GitHub：挂接、re-parent、label、发布自检 | references/mechanics.md | 仅当本次不落 GitHub（纯草稿）或目标平台不是 GitHub——机制不适用，但发布自检一节在任何落地前仍要过 |

## 思维方式

1. **格式即调查清单**：某区块写不出来 = 对应调查没做。格式的作用是让缺口在写作时暴露，而不是在 headless 执行时暴露。
2. **目标完备，不是实现完备**：收敛自由裁量靠 a 类写全 + 目标级决策裁决 + 性质表述，不靠预钉实现。
3. **自包含优先于 DRY**：headless 读者打开一个 thread 就拿到全部所需。
4. **对抗审查是格式的检验环**：连续一轮无新发现才算干涸；「没有发现」也是必须记录的结论。
5. **操作员输入是镜头修正**：重新定义衡量尺，不是任务追加。响应顺序：实证校验新镜头 → 指名旧产出哪里复读了旧误解 → 重扫全部产出 → 报告区分「新发现 / 修正 / 重验通过」。
6. **怀疑先核实**：每个判断落 issue 前在代码里核实；落空的怀疑登记为正例，与坐实的漏洞同样有信息量。
7. **方法自身用生成性基准迭代**：拿**不是从本方法蒸馏出来的**真实工件（操作员手笔的 RFC 树）测试——给定方向，逐区块问「方法会引出这段内容吗」；引不出的就是方法缺口。从方法自身的来源工件测只会得到循环确认。
